# 如何优雅地进行 i18n

> [!WARNING]
> 本文档由中文机器翻译而来。虽然我们力求准确，但翻译中可能存在一些不完善之处。

## 使用 i18n Ally 插件增强开发体验

i18n Ally 是一个强大的 VSCode 扩展，在开发过程中提供实时反馈，帮助开发者更早发现缺失或错误的翻译。

该插件已在项目中配置——只需安装即可开始使用。

### 开发期间的优势

- **实时预览**：翻译文本直接显示在编辑器中。
- **错误检测**：自动跟踪并突出显示缺失的翻译或未使用的 key。
- **快速导航**：通过 Ctrl/Cmd + 点击跳转到 key 定义。
- **自动补全**：输入 i18n key 时提供建议。

## i18n 约定

### **不惜一切代价避免扁平结构**

永远不要使用像 `"add.button.tip": "Add"` 这样的扁平结构。相反，采用清晰的嵌套结构：

```json
// 错误 - 扁平结构
{
  "add.button.tip": "Add",
  "delete.button.tip": "Delete"
}

// 正确 - 嵌套结构
{
  "add": {
    "button": {
      "tip": "Add"
    }
  },
  "delete": {
    "button": {
      "tip": "Delete"
    }
  }
}
```

#### 为什么使用嵌套结构？

1. **自然分组**：相关文本通过对象嵌套按上下文逻辑分组。
2. **插件要求**：像 i18n Ally 这样的工具需要扁平或嵌套格式才能正确分析翻译文件。

### **避免在 `t()` 中使用模板字符串**

**我们强烈建议不要使用模板字符串进行动态插值。**虽然在一般 JavaScript 开发中很方便，但它们在 i18n 场景中会导致几个问题。

#### 1. **插件无法跟踪动态 Key**

像 i18n Ally 这样的工具无法解析模板字符串中的动态内容，导致：

- 无实时预览
- 无法检测缺失的翻译
- 无法导航到 key 定义

```javascript
// 不推荐 - 插件无法解析
const message = t(`fruits.${fruit}`);
```

#### 2. **编辑器中无实时渲染**

模板字符串在 IDE 中显示为原始代码而不是最终的翻译文本，降低了开发体验。

#### 3. **更难维护**

由于插件无法跟踪此类用法，开发者必须手动验证语言文件中是否存在相应的 key。

### 推荐方法

为避免缺失 key，所有动态翻译的文本应首先维护一个 `FooKeyMap`，然后通过函数检索翻译文本。

例如：

```ts
// src/renderer/i18n/label.ts
const themeModeKeyMap = {
  dark: "settings.theme.dark",
  light: "settings.theme.light",
  system: "settings.theme.system",
} as const;

export const getThemeModeLabel = (key: string): string => {
  return themeModeKeyMap[key] ? t(themeModeKeyMap[key]) : key;
};
```

通过避免模板字符串，你可以获得更好的开发者体验、更可靠的翻译检查和更易维护的代码库。

## 自动化脚本

项目包含几个脚本来自动化 i18n 相关任务：

### `i18n:check` - 验证 i18n 结构

此脚本检查：

- 所有语言文件是否使用嵌套结构
- 缺失或未使用的 key
- key 是否正确排序

```bash
pnpm i18n:check
```

### `i18n:sync` - 同步 JSON 结构和排序顺序

此脚本使用 `zh-cn.json` 作为真实来源来同步所有语言文件的结构，包括：

1. 添加缺失的 key，使用占位符 `[to be translated]`
2. 删除过时的 key
3. 自动排序 key

```bash
pnpm i18n:sync
```

### `i18n:unused` - 查找未使用的 Key

此脚本扫描代码库中的 i18n key 引用，并报告 `zh-cn.json` 中存在但在源代码中找不到的 key。

此命令仅打印报告，不修改任何文件：

```bash
pnpm i18n:unused
```

报告包括：

- 未使用 key 总数
- 按顶级命名空间分组的未使用 key 数量
- 每个命名空间的几个示例 key

要获得机器可读的输出，使用 JSON 模式：

```bash
pnpm i18n:unused --json
```

#### 清理未使用的 Key

当你想删除未使用的 key 时，使用 `i18n:remove-unused`。清理是可选的，仅通过此删除命令运行。

运行交互式清理：

```bash
pnpm i18n:remove-unused
```

提示会列出顶级命名空间，例如 `common`、`settings` 或 `translate`。选择一个或多个命名空间以仅删除这些组中未使用的叶子 key。

针对特定命名空间运行非交互式清理：

```bash
pnpm i18n:remove-unused --groups common,settings
```

针对所有未使用的 key 运行非交互式清理：

```bash
pnpm i18n:remove-unused --all
```

清理会更新两个目录：

- `src/renderer/i18n/locales/*.json`
- `src/renderer/i18n/translate/*.json`

删除后，脚本会修剪空对象并排序 key，以保持文件与现有 i18n 格式一致。

#### 什么算作已使用

扫描器识别常见的静态 i18n 模式：

- `t("key")` 和 `i18n.t("key")`
- `<Trans i18nKey="key" />`
- Key 字段如 `titleKey`、`labelKey`、`descriptionKey`、`messageKey` 和 `i18nKey`
- `src/renderer/i18n/label.ts` 中已知的标签映射
- 像 `t("key")` 这样的注释引用，保持 i18n Ally 样式的显式引用有效
- 从 `SHORTCUT_DEFINITIONS` 派生的快捷键标签
- 条件翻译调用如 `t(condition ? "a.key" : "b.key")`
- 可以保守匹配的静态模板表达式命名空间
- 扫描的源文件中任何地方的精确完整 key 文本匹配

精确文本匹配故意保守：如果完整的 key 字符串出现在源代码中，该 key 被视为已使用。这可能会保留一些真正未使用的 key，但它避免删除通过辅助映射、间接调用或动态代码路径引用的 key。

#### 安全清理工作流

1. 运行 `pnpm i18n:unused` 并审查分组报告。
2. 如果一个 key 看起来可疑，在清理前在源代码中搜索确切的 key。
3. 一次只清理一个小命名空间，使用 `pnpm i18n:remove-unused --groups <namespace>`，或在已审查完整报告后使用 `pnpm i18n:remove-unused --all`。
4. 审查 JSON diff。
5. 清理后运行 `pnpm i18n:check`。

### `i18n:translate` - 自动翻译待处理文本

此脚本使用机器翻译填充标记为 `[to be translated]` 的文本。

通常，在 `zh-cn.json` 中添加新文本后，运行 `i18n:sync`，然后运行 `i18n:translate` 以完成翻译。

使用此脚本前，设置所需的环境变量：

```bash
API_KEY="sk-xxx"
BASE_URL="https://dashscope.aliyuncs.com/compatible-mode/v1/"
MODEL="qwen-plus-latest"
```

或者，直接将这些变量添加到你的 `.env` 文件中。

```bash
pnpm i18n:translate
```

### 工作流程

1. 开发期间，首先在 `zh-cn.json` 中添加所需的文本
2. 确认它在中文环境中显示正确
3. 运行 `pnpm i18n:sync` 将 key 传播到其他语言文件
4. 运行 `pnpm i18n:translate` 执行机器翻译
5. 喝杯咖啡，让魔法发生！

## 最佳实践

1. **使用中文作为源语言**：所有开发从中文开始，然后翻译到其他语言。
2. **提交前运行检查脚本**：使用 `pnpm i18n:check` 尽早发现 i18n 问题。
3. **小批量翻译**：避免积累大量未翻译内容。
4. **保持 Key 语义清晰**：Key 应清楚表达其目的，例如 `user.profile.avatar.upload.error`
