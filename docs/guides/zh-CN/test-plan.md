# 测试计划

为了给用户提供更稳定的应用体验和更快的迭代速度，Magic Box 推出了"测试计划"。

## 用户指南

测试计划分为 RC 通道和 Beta 通道，区别如下：

- **RC (Release Candidate)**：功能稳定，bug 较少，接近正式发布。
- **Beta**：功能可能随时变化，可能有更多 bug，但用户可以更早体验未来功能。

用户可以在软件的 `设置` > `关于` 中启用"测试计划"并选择版本通道。请注意，"测试计划"中的版本无法保证数据一致性，因此在使用前务必备份数据。

启用 RC 通道或 Beta 通道后，如果发布了稳定版本，用户仍将升级到稳定版本。

欢迎用户针对测试中遇到的任何 bug 提交 issue 或通过其他渠道提供反馈。您的反馈对我们非常重要。

## 开发者指南

### 参与测试计划

开发者应根据[贡献者指南](../../../CONTRIBUTING.md)提交 `PR`（并确保目标分支为 `main`）。仓库维护者将根据功能对应用的影响、重要性以及是否需要更广泛测试等因素评估 `PR` 是否应包含在测试计划中。

如果 `PR` 被添加到测试计划，仓库维护者将：

- 通知 `PR` 提交者。
- 将 PR 设置为 `draft` 状态（以避免在测试完成前意外合并到 `main`）。
- 将 `milestone` 设置为特定的测试计划版本。
- 修改 `PR` 标题。

在参与测试计划期间，`PR` 提交者应：

- 保持 `PR` 分支与最新的 `main` 同步（即 `PR` 分支应始终基于最新的 `main` 代码）。
- 确保 `PR` 分支无冲突。
- 积极响应评论和评审并修复 bug。
- 启用维护者修改 `PR` 分支的权限，以便随时修复 bug。

包含在测试计划中并不保证 `PR` 的最终合并。它可能因功能不成熟或测试反馈不佳而被搁置。

### 测试计划负责人

一个维护者将被指定为特定版本（例如 `1.5.0-rc`）的负责人。测试计划负责人的职责包括：

- 确定 `PR` 是否满足测试计划要求并决定是否应包含在当前测试计划中。
- 修改添加到测试计划的 `PR` 的状态并与 `PR` 提交者沟通相关事项。
- 在测试计划发布前，将添加到测试计划的 `PR` 的分支（使用 squash merge）合并到 `testplan` 的相应版本分支中并解决冲突。
- 确保 `testplan` 分支与最新的 `main` 同步。
- 监督测试计划发布。

## 深入理解

### 关于 `PR`

`PR` 是特定分支（和提交）、评论、评审和其他信息的集合，它是测试计划的**最小管理单元**。

与将所有功能提交到单个分支相比，测试计划通过 `PR` 管理功能，这提供了更大的灵活性和效率：

- 功能可以在不同版本的测试计划之间添加或删除，无需繁琐的 `revert` 操作。
- 建立了明确的功能边界和责任。Bug 修复在各自的 `PR` 内完成，隔离交叉影响并更好地跟踪进度。
- `PR` 提交者负责解决与最新 `main` 的冲突。测试计划负责人负责解决 `PR` 分支之间的冲突。然而，由于添加到测试计划的功能相对独立（换句话说，如果一个功能有广泛影响，它应该单独包含在测试计划中），冲突通常很少或很简单。

### `testplan` 分支

`testplan` 分支是用于测试计划发布的**临时**分支。

注意：

- **不要基于此分支开发**。它可能随时更改甚至被删除，不保证提交的完整性或顺序。
- **不要向此分支提交 `commits` 或 `PR`**，因为它们不会被保留。
- `testplan` 分支始终基于最新的 `main` 分支（不是基于发布的版本），在此基础上添加功能。

#### RC 分支

分支名称：`testplan/rc/x.y.z`

用于 RC 发布，其中 `x.y.z` 是目标版本号。请注意，无论是 rc.1 还是 rc.5，只要主版本号是 `x.y.z`，它都在此分支中完成。

通常，从此分支发布的版本号命名为 `x.y.z-rc.n`。

#### Beta 分支

分支名称：`testplan/beta/x.y.z`

用于 Beta 发布，其中 `x.y.z` 是目标版本号。请注意，无论是 beta.1 还是 beta.5，只要主版本号是 `x.y.z`，它都在此分支中完成。

通常，从此分支发布的版本号命名为 `x.y.z-beta.n`。

### 版本规则

测试计划的应用版本号为：`x.y.z-CHA.n`，其中：

- `x.y.z` 是常规版本号，此处称为**目标版本号**。
- `CHA` 是通道代码（Channel），当前分为 `rc` 和 `beta`。
- `n` 是发布编号，从 `1` 开始。

完整版本号示例：`1.5.0-rc.3`、`1.5.1-beta.1`、`1.6.0-beta.6`。

测试计划的**目标版本号**指向预期添加这些功能的正式版本号。例如：

- `1.5.0-rc.3` 表示这是 `1.5.0` 正式版的预览（当前最新正式版本是 `1.4.9`，`1.5.0` 尚未正式发布）。
- `1.5.1-beta.1` 表示这是 `1.5.1` 正式版的 beta 版本（当前最新正式版本是 `1.5.0`，`1.5.1` 尚未正式发布）。
