# 远程请求安全

主进程直接发起的 URL 请求可能接收来自渲染进程、助手或提供商所控制的输入。对这些路径进行字面 URL 检查是不够的：攻击者控制的主机名可能在预检期间解析为公网地址，然后在网络栈建立连接时重新绑定到私有地址。

## 直接请求规则

主进程对不可信 HTTP(S) URL 的直接请求必须：

- 拒绝非 HTTP(S) 协议及 URL 中内嵌的凭据；
- 拒绝 localhost、私有地址、链路本地地址、多播地址、保留地址及未指定的字面 IP 目标；
- 在建立请求前解析主机名的 DNS 结果；
- 若任意已解析地址属于本地或私有地址，则拒绝该请求；
- 在保留原始 `Host` 头和 TLS SNI 的同时，将实际连接绑定到预验证地址；
- 默认拒绝重定向；
- 在主进程缓冲响应体之前限制其大小。

## 为何不使用 `net.fetch`

Electron 的 `net.fetch` 使用 Chromium 网络栈并遵循应用/会话的代理配置，但它不暴露每个请求的 DNS `lookup` 钩子。因此，先进行 DNS 预检再调用 `net.fetch(originalUrl)` 仍然存在 DNS 检查时间与使用时间（TOCTOU）的竞争漏洞。

对于直接的不可信请求，Magic Box 使用 Node HTTP(S) 请求路径，将连接固定到已验证的公网 DNS 答案。这有意以牺牲完整 Chromium 会话代理兼容性为代价，优先保障针对这些直接提供商请求的 SSRF 防护。仅在连接保护对实际使用地址仍然有效的前提下，才可日后补充代理兼容的请求方式。

从 `net.fetch` 迁移的调用方必须将其视为用户可感知的兼容性变更：`fetchRemoteText` 不继承 Chromium 会话代理设置。不要添加调用方专属的 `net.fetch` 回退，因为这会重新引入 DNS TOCTOU 漏洞。在仅有代理的网络环境中，引文预览会有意降级为空白预览内容，但引文标题和链接仍可正常使用。

## 重定向

默认拒绝重定向。调用方可选择启用严格的跳转次数上限；每次跟随跳转都会在建立下一个请求之前重新执行 URL 验证、DNS 解析、私有地址拒绝及固定连接建立。
